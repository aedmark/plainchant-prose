# Documentation map

Each project fact has one authoritative home. Other documents link to that owner instead of maintaining a second copy.

## Audiences and ownership

| Document | Primary audience | Owns | Does not own |
| --- | --- | --- | --- |
| `../BRIEF.md` | Maintainer and product designer | Original requested product and feature scope | Later decisions, implementation detail, or session state |
| `../LICENSE` | Users and distributors | Permission, conditions, warranty disclaimer, and contribution acknowledgment | Contribution workflow or security reporting |
| `../README.md` | Newcomers | Purpose, boundary, current entry points | Internal workflow or detailed architecture |
| `../AGENTS.md` | Contributors and coding agents | Standing rules, authority, conventions, protected areas | Feature history or design rationale |
| `../ROADMAP.md` | Maintainers and contributors | Planned scope, order, gates, and item status | Component contracts or current test results |
| `HANDOFF.md` | The next work session | Current repository state, evidence, immediate next steps, recent sessions | Permanent design rules |
| `ARCHITECTURE.md` | Developers and reviewers | Planned and implemented system shape, interfaces, invariants, state, failure modes | Choice history or chronological progress |
| `DECISIONS.md` | Future decision-makers | Accepted and proposed choices, alternatives, consequences, tensions, questions | Routine implementation detail |
| `TESTING.md` | Contributors and release owners | Commands, proof boundaries, fixtures, methods, pitfalls | A duplicate of dated test results |
| `SECURITY.md` | Users and developers | Assets, threats, secure defaults, reporting and response | Full incident evidence or general architecture |
| `CONTRIBUTING.md` | Human and automated contributors | Shared setup, change, verification, and submission workflow | Agent-only rules |
| `CHANGELOG.md` | Users | Implemented user-visible changes by release | Plans, commit history, or documentation-only work |
| `archive/` | Investigators | Historical sessions, retired plans, and lineage digests | Current instructions or design |

## Update triggers

| Change | Required documentation |
| --- | --- |
| Maintainer changes the requested product | BRIEF only with explicit permission; then reconcile all affected owners |
| User-visible implemented behaviour | README if onboarding changed; CHANGELOG; relevant help when it exists |
| Component, interface, dependency, data flow, state, or failure-mode change | ARCHITECTURE |
| Durable tradeoff, accepted proposal, reversal, or resolved tension | DECISIONS; mark superseded or resolved history without deleting it |
| Test command, fixture, proof boundary, environment, or pitfall change | TESTING |
| Threat, trust boundary, retention rule, dependency, reporting path, or incident process change | SECURITY |
| Work starts, pauses, or materially changes repository state | HANDOFF; roadmap status when applicable |
| Contribution, authority, branch, commit, or release workflow change | CONTRIBUTING and AGENTS when agents are affected |
| Licence grant, attribution, or disclaimer change | LICENSE and a decision; README if the public summary changes |
| New planned work or changed gate | ROADMAP, with origin and acceptance evidence |
| Completed roadmap phase or an overlong session log | Move exact history to `archive/` and leave a pointer |

## Planned optional documents

Create these only when their roadmap item produces real content, then add them to the ownership table:

- `docs/archive/plainchant-lineage.md` at `P0-03`, for copied-file lineage and relevant upstream traps;
- source-format reference or schema generated by `P1-01`, if the grammar outgrows ARCHITECTURE;
- user help at `P5-06`, derived from implemented behaviour;
- platform runbooks if packaging, release, migration, or recovery requires a repeatable procedure;
- sanitized incident reviews when an event produces durable lessons.

## Style and evidence

- Lead with the reader's task or current truth.
- Use declarative present tense, commas and semicolons instead of em dashes, and direct names instead of rhetorical
  contrasts.
- Label planned paths and commands until they exist. Never describe a blueprint component as implemented.
- Keep the brief's facts distinct from adopted decisions and proposed designs.
- Identify the command, date, environment, source commit, or external-tool version behind volatile claims.
- Link to the authoritative owner. If a summary is necessary, say which document owns the complete rule.
- Keep private manuscripts, secrets, personal paths, private URLs, and raw incident data out of documentation.
- A clean Manifold check proves internal document consistency; only code tests and real workflow evidence prove
  implementation claims.
